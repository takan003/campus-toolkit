## 一、外掛模組架構概述

外掛模組是獨立的 GAS 網頁應用程式，擁有自己的試算表與部署。  
主系統提供**啟用功能**，讓管理員只需提供兩項資訊，即可將模組整合進角色首頁的入口卡牌。

**核心原則：管理員的操作越少越好，其餘交給程式自動處理。**

---

## 二、整體架構

```
┌─────────────────────────┐      活化（一次性）
│  主系統（數位校園GAS站）  │ ◄──────────────────  ┌─────────────────┐
│                         │   提供試算表連結        │  外掛模組 A     │
│  ● 設定工作表           │   提供部署網址          │  ● 設定工作表    │
│  ● 功能模組工作表        │   自動寫入 TOKEN_SECRET│  ● auth.js      │
│  ● auth.js             │                       │  ● main.js      │
│  ● sessionSign()       │                       └────────┬────────┘
│                         │                               │
│  使用者點選卡牌           │                               │
│  ● 產生簽章 Token       │ ──► 傳遞參數(方案B) ────────►  │
│  ● payload: 身分+設定    │   導向模組部署網址?token=xxx    │
│                         │                               ▼
│                         │                       模組存入 localStorage
│                         │                       供內部轉頁使用
└─────────────────────────┘
```

**兩次互動：**
1. **活化（一次性）**：管理員填入兩項資訊，系統將 TOKEN_SECRET 寫入模組試算表
2. **使用（每次點選）**：主系統簽署 Token（含身分+設定參數），導向模組驗證後使用

## 三、活化流程（一次性）

### 3.1 管理員提供的資訊

| 欄位 | 說明 | 範例 |
|------|------|------|
| 模組試算表雲端連結 | 模組所使用的 Google 試算表網址 | `https://docs.google.com/spreadsheets/d/abc123` |
| 模組部署網址 | 模組部署成網頁應用程式後的網址 | `https://script.google.com/macros/s/xyz/exec` |

### 3.2 模組資訊工作表

模組試算表中必須存在名為「模組資訊」的工作表，格式為**兩欄 Key-Value**：

| 欄位 | 型態 | 說明 |
|------|------|------|
| A 欄（標題） | 文字 | 欄位名稱 |
| B 欄（值） | 文字 | 對應的內容值 |

> 列順序不固定（用戶可能亂動），以 A 欄標題文字比對為準。

必備欄位：

| 標題（A 欄） | B 欄格式 | 說明 |
|-------------|----------|------|
| 模組名稱 | 純文字 | 程式內部名稱，字母數字底線 |
| 顯示名稱 | 純文字 | 顯示在入口卡牌上的名稱 |
| 管理員 | `是,是` | 第1個值=是否有此功能，第2個值=是否顯示功能入口，以半形逗號分隔 |
| 教職員 | `是,是` | 同上 |
| 學生 | `是,是` | 同上 |

選填欄位（拷入主系統「模組」工作表的對應欄位，無則留空）：

| 標題（A 欄） | 說明 |
|-------------|------|
| 模組版本 | 版本號文字 |
| 模組日期 | 發布日期文字 |
| 模組作者 | 作者姓名 |
| 作者電子郵件地址 | 作者聯絡信箱 |
| 作者個人網址 | 作者網站或專案網址 |
| 單位分類 | 單位類別標籤 |
| 承辦分類 | 承辦業務類別標籤 |

### 3.3 系統自動完成的工作

當管理員點選「安裝模組」時，主程式依序執行：

```
Step 1  透過 SpreadsheetApp.openByUrl() 開啟模組試算表
Step 2  找到名為「模組資訊」的工作表
Step 3  讀取所有欄位（A 欄為標題，B 欄為值），比對標題名稱逐欄取出
        其中「管理員」「教職員」「學生」三個欄位的 B 欄格式為「是,是」，
        以半形逗號 split 後，第1個值為「功能」開關，第2個值為「顯示」開關
Step 4  將主系統的 TOKEN_SECRET 寫入模組的「設定」工作表（欄位名稱 TOKEN_SECRET）
Step 5  從「模組部署網址」中提取部署 ID（正則匹配 /[-\w]{25,}/）
Step 6  在「功能模組」工作表中新增一列，將 Step 3 的所有欄位拆分寫入：
        - 一般欄位直接拷貝
        - 「管理員/教職員/學生」分別寫入「管理員功能/教職員功能/學生功能」欄位（保留原始值）
        - 「管理員顯示/教職員顯示/學生顯示」欄位強制寫入「否」
        - 再加上管理員輸入的試算表連結、部署網址、提取的部署 ID、啟用狀態「是」、最後同步時間

> **安裝完成後提示管理員：** 三個身分的「顯示功能入口」目前均為「否」，請至模組管理頁面手動開啟。
```

**管理員完全不需要手動編輯模組的試算表或設定任何金鑰。**

### 3.4 卸載流程

當管理員點選「卸載模組」時：

```
Step 1  從「功能模組」工作表刪除該模組的整列資料
Step 2  （模組試算表保留原樣，不刪除任何資料）
```

> 卸載只影響主系統的入口列表，不碰模組本身的試算表。

### 3.5 安裝前後的資料流向

```
管理員輸入：
  模組試算表雲端連結 ──────┐
  模組部署網址 ──────┐     │
                     │     │
                     ▼     ▼
              主程式開啟模組試算表
                     │
                     ▼
              讀取「模組資訊」工作表
              ┌─────────────────────┐
              │ 模組名稱            │──┐
              │ 顯示名稱            │──┤
              │ 管理員 / 教職員 / 學生│──┤
              │ 模組版本 / 日期     │──┤
              │ 模組作者 / 信箱 / 網址│──┤
              │ 單位分類 / 承辦分類  │──┤
              └─────────────────────┘  │
                                        │
              ┌──────────────────┐      │
              │ TOKEN_SECRET     │──┐   │
              └──────────────────┘  │   │
                     │              │   │

              ┌──────────────────────────┐
              │ 主系統「模組」工作表       │
              │ 寫入所有欄位             │
```

### 3.6 安裝前後的比較

| 項目 | 安裝前 | 安裝後 |
|------|--------|--------|
| 模組設定工作表的 TOKEN_SECRET | 未設定 | 自動寫入，與主系統同值 |
| 主系統功能模組工作表 | 無此模組記錄 | 完整一列，含所有模組資訊 |
| 角色顯示開關 | — | 三個身分的「顯示功能入口」均強制為「否」 |
| 安裝資料流向 | — | 模組 → 主系統（模組資訊工作表全欄位）<br>主系統 → 模組（TOKEN_SECRET） |

## 四、使用者點選流程（每次使用）— 方案B（參數傳遞）

當使用者（已登入）在角色首頁點選外掛模組的入口卡牌時：

```
Step 1  主系統從 session 取得 email、role、name
Step 2  從「設定」工作表讀取學校設定參數
Step 3  呼叫 sessionSign() 產生簽章 Token
         payload = {
           email, role, name,
           學校全稱, 學校簡稱, 系統自命名,
           學年度, 教育部學校代碼,
           承辦師長, 承辦師長電子郵件地址,
           原創版權宣告, 贊助廣告開關,
           主系統部署網址,        ← ScriptApp.getService().getUrl()
           iat, exp
         }
Step 4  導向模組部署網址：
         模組部署網址?token=xxxxx
```

**URL 只有一個參數 `token`，乾淨簡潔。**

### 4.1 模組端的參數處理

模組 `doGet` 收到 token 後：

```
Step 1  從自身的「設定」工作表讀取 TOKEN_SECRET
Step 2  使用 sessionVerify(token, TOKEN_SECRET) 驗證簽章
Step 3  驗證成功 → 取出 payload 中的所有參數
Step 4  將參數存入 localStorage（模組內轉頁不再需要攜帶參數）
Step 5  驗證失敗 → 導回主系統重新登入
```

### 4.2 localStorage 存取方式

模組前端範例：

```javascript
// doGet 傳入 template
var moduleConfig = <?!= JSON.stringify(payload) ?>;
localStorage.setItem('moduleConfig', JSON.stringify(moduleConfig));

// 模組內部任何頁面讀取
var cfg = JSON.parse(localStorage.getItem('moduleConfig'));
console.log(cfg['學校全稱']);
```

**模組內轉頁只需讀 localStorage，不需每頁攜帶主系統參數。**

## 五、傳遞 vs 拷貝的最終分工

| 項目 | 方式 | 說明 |
|------|------|------|
| email / role / name | 傳遞（Token payload） | 登入後從成員名冊取得的資料 |
| 學校全稱 / 學校簡稱 / 系統自命名 | 傳遞（Token payload） | 設定工作表 |
| 學年度 / 教育部學校代碼 | 傳遞（Token payload） | 設定工作表 |
| 承辦師長 / 承辦師長電子郵件地址 | 傳遞（Token payload） | 設定工作表 |
| 原創版權宣告 / 贊助廣告開關 | 傳遞（Token payload） | 設定工作表 |
| 主系統部署網址 | 傳遞（Token payload） | 主系統自動抓取 |
| 成員名冊雲端連結 | 傳遞（Token payload） | 主系統設定工作表，模組以此 `openById` 讀同一張成員名冊 |
| **TOKEN_SECRET** | **拷貝（活化寫入模組試算表）** | 不該暴露在 URL 上，寫入模組設定工作表 |

## 六、身分傳遞機制

| 項目 | 選擇 |
|------|------|
| 傳遞方式 | URL 參數 `?token=xxx` |
| Token 格式 | HMAC-SHA256 簽章（沿用主系統 `sessionSign`） |
| Token payload | 身分（email+role+name）+ 設定參數（學校資訊、承辦資訊） |
| 有效期限 | 2 小時（與主系統 session 一致） |
| 金鑰來源 | 活化時自動寫入模組設定工作表，人為零操作 |

### 安全特性

- Token 無法偽造（需要 TOKEN_SECRET 才能簽署）
- Token 有過期時間，無法永久使用
- token payload 經 base64url 編碼，不含特殊字元，不影響 URL 傳遞
- TOKEN_SECRET 存放在模組設定工作表中，僅限具編輯權限者查看

## 八、模組端應遵循的規範

若要能與主系統整合，外掛模組的 GAS 專案必須：

1. **包含 `auth.js`**（或等效的 `sessionVerify` 函式）
2. **在「設定」工作表中定義 `TOKEN_SECRET` 欄位**
   - 活化時主系統會寫入此欄位
   - 欄位名稱必須為 `TOKEN_SECRET`
3. **在 `doGet` 中處理 `?token=` 參數**
   - 從設定工作表讀取 `TOKEN_SECRET`
   - 驗證 token
   - 驗證成功後將 payload 存入 localStorage
   - 驗證失敗則導回主系統
4. **模組內部轉頁從 localStorage 讀取設定參數**
   - 不需每頁攜帶主系統參數

### 建議的設定工作表結構

```
         A                  B
1   學校全稱              xxx學校
2   學校簡稱              xxx
3   系統自命名            數位校園GAS站
4   學年度                114
5   TOKEN_SECRET         （活化時自動寫入）
6   主系統部署網址         （token 傳遞，非拷貝）
7   （模組自訂欄位）       （模組自訂值）
```

> 注意：`學校全稱`、`學校簡稱` 等設定欄位在模組設定工作表中**可選**（供模組離線備用），實際最新值由 token 每次傳遞。

## 八之一、CSS 主題細緻化協議（模組開發者共同遵守）

> 完整規劃與討論紀錄見大本營根目錄 `CSS主題細緻化規劃書.md`。本章為模組開發者**必須遵守**的協議摘要。

> **115.08.16 補充**：主題清單（抽屜選單）每筆需顯示**來源標籤**（內建/市集/自訂/匯入），與主程式一致——設計見 `CSS主題細緻化規劃書.md` §10.7。

### 8-1.1 主題優先級解析規則（核心）

模組內的 CSS 主題依下列優先級解析，**由高至低**：

```
模組強制（模組「設定」工作表 CSS主題ID 欄位）        ← 模組強制贏（定案）
  > 主程式強制（token 帶的主程式強制主題）
  > 使用者帳號主題欄位（模組成員名冊 CSS主題ID 欄位）
  > token 帶的主程式使用者主題（主程式已解析的用戶主題）
  > localStorage（gasThemeActive）
  > 模組系統預設
```

- **越靠近使用者端越優先**：模組的設定比主程式更特定，故模組強制置頂
- **強制主題絕對化**：強制欄位有值時，用戶自訂與 localStorage 全部失效
- **空值即不介入**：所有 `CSS主題ID` 欄位一律「空值 = 不強制 / 不套用」

### 8-1.2 「設定」工作表新增欄位（Admin 強制）

| 欄位 | 型態 | 說明 |
|------|------|------|
| `CSS主題ID` | 文字 | 空值 = 不強制；有值 = 該模組全體強制套用此主題，用戶自訂失效 |

- 範例值：`builtin:dark`、`custom:xxxx-xxxx`、`market:xxxx-xxxx`
- 沿用既有慣例：列順序不固定，以 A 欄標題文字比對為準（`getDataR('設定')`）
- 主程式「設定」工作表亦有同名欄位（強制主程式全體），兩者獨立運作

### 8-1.3 成員名冊新增欄位（用戶自訂）

模組讀的是**獨立「成員名冊」試算表**（與主程式**同一張**，非模組主試算表內的工作表），依身分工作表（學生/教職員/管理員）取得該帳號的個人主題：

| 欄位 | 型態 | 說明 |
|------|------|------|
| `CSS主題ID` | 文字 | 空值 = 不套用；有值 = 該帳號套用此主題 |

- 模組**不自行設定**名冊連結：由主程式簽發模組 token 時，於 payload 附帶「成員名冊雲端連結」（主系統設定工作表同名欄位），模組 `openById` 取得（需模組專案帳號對該試算表有檢視權限）
- token 未帶連結／名冊缺欄位／找不到帳號列：一律**靜默跳過**名冊（讀取回空、寫入跳過），不影響其他功能
- ✅ 主程式成員名冊的 3 種身分工作表（學生/教職員/管理員）**已手動新增** `CSS主題ID` 欄位；同一張試算表即模組所讀，兩邊共享同一份個人主題資料

### 8-1.4 token 傳遞協議（不變）

- token 機制維持現行方案 B（`?token=xxx`），**不做結構性改變**
- token payload **新增一欄 `themeId`**：主程式登入後已解析出的最終主題 ID（已含主程式強制、主程式名冊欄位）
- 模組收到 token 後，在 §8-1.1 的優先級上疊加：模組強制 / 模組名冊欄位可蓋過 token 帶的主程式主題，否則沿用 token 的 `themeId`

### 8-1.5 前端初始化順序（theme.html）

`theme.html` 初始化解析順序改為：

```javascript
var tid = forced || userTheme || tokenTheme || localStorage.getItem('gasThemeActive') || def;
// forced    = 模組「設定」CSS主題ID（強制）|| 主程式強制（token 帶）
// userTheme = 模組名冊 CSS主題ID（帳號欄位，伺服端注入）
// tokenTheme = token 帶的主程式已解析主題
// def       = 模組系統預設
```
（頁面以 `window.GAS_FORCED_THEME` / `GAS_USER_THEME` / `GAS_TOKEN_THEME` / `GAS_DEFAULT_THEME` 全域注入，**必須在 `include('theme')` 之前**）

> ⚠️ **注入順序鐵律（實測踩坑紀錄）**：`include('theme')` 會在模板處理當下把 theme.html 的初始化 IIFE 直接輸出並執行；若全域注入寫在 include **之後**，初始化時全域變數尚未定義 → 全部退回 localStorage 兜底，**帳號欄位與強制主題形同虛設**（主程式 5 個 session 頁曾因此長期失效，部署 @240 修復）。注入必須寫在 include 之前；偵錯時可在抽屜顯示 `GAS_USER_THEME` 等實際值確認。

- 未登入 / 公開頁面：`userTheme` 為空，自動退回 localStorage → 系統預設
- 主題切換抽屜：模組或主程式有強制主題時隱藏（沿用 `_forcedTheme` 判斷）

### 8-1.6 模組內主題切換（開放）

- 模組開放「主題」切換抽屜（`toggleThemeDrawer` 已內建）
- 切換後寫回**成員名冊試算表**（token 帶的「成員名冊雲端連結」，與主程式同一張）的 `CSS主題ID` 欄位（防抖呼叫 `google.script.run.updateUserTheme`，僅登入且非強制時）
- **同步主程式（已實作）**：`updateUserTheme` 內部另呼叫 `syncThemeToMain(token, themeId)` → 對主程式部署網址（token 帶的 `主系統部署網址`）POST `{page: 'theme_sync', token, themeId}`，主程式驗證簽章後寫入**主程式名冊**的 `CSS主題ID`，做到「改一處、全生態一致」
- 成員名冊試算表未取得／缺 `CSS主題ID` 欄位／找不到帳號列時：`updateUserTheme` 自動跳過名冊寫入、僅同步主程式（不報錯）

### 8-1.6.1 主程式 theme_sync 端點（模組開發者呼叫契約）

| 項目 | 內容 |
|------|------|
| 方法 | POST `{主程式部署網址}` |
| 參數 | `page=theme_sync`、`token`（主程式發給模組的模組 token）、`themeId`（`builtin:`／`market:` 開頭） |

| 用途 | 模組內切換主題 → 同步主程式名冊，使用者回主程式立即套用（主程式每頁面載入會重讀名冊欄位） |

## 附錄 C：考試報名系統模組文件

### 導師首頁顯示學生報名情形 — 可行性分析

#### 需求

導師進入首頁時，在班級學生列表中直接看到每位學生的簡易報名情形（已報名／不報名／尚未報名），不需逐一點開。

#### 環境限制

- Google Apps Script（GAS）前端呼叫後端為同步 RPC
- `getClassStudentList()` 是目前唯一被呼叫的後端函式
- 資料來源：Google 試算表（SpreadsheetApp）

#### 數據規模（以普通高中估算）

| 項目 | 數量 |
|------|------|
| 班級人數 | 35 人 |
| 考試管道 | 7 個 |
| 每人平均報名 | 3–4 個管道 |
| 總報名紀錄 | ~120 筆（35人 × 3.5） |
| 每個管道工作表的列數 | ≈ 全學年學生數（如 600 列） |

#### 方案設計

##### 現狀

```
getClassStudentList()
  └─ 讀取「學生」工作表 → 回傳 35 筆學生資料
```

##### 改動後

```
getClassStudentList()
  ├─ 讀取「學生」工作表 → 回傳 35 筆學生資料
  └─ 讀取 N 個管道工作表（每 sheet 一次 getValues()）
     └─ 在記憶體中建立 HashMap：{學號 → 各管道報名情形}
        └─ 回傳至前端
```

**不採用**的方案：對每個學生逐個查詢 → 35 ×（N 個管道）× 次查詢 → 太慢。

#### 耗時分析（GAS 執行時間）

##### 基準：現有 `getClassStudentList()`

| 操作 | 估計時間 |
|------|---------|
| session 驗證 | ~50ms |
| 讀取「導師」工作表 | ~100ms |

### 學生報名情形管理增益建議書

#### 一、需求背景

#### 二、環境限制

- Google Apps Script（GAS）前端呼叫後端為同步 RPC
- `getClassStudentList()` 是目前唯一被呼叫的後端函式
- 資料來源：Google 試算表（SpreadsheetApp）

#### 三、數據規模

| 項目 | 數值 |
|------|------|
| 全校學生數 | 500 人 |
| 班級數（估算） | ~14 班（每班 ~35 人） |
| 考試管道 | 7 個 |
| 每人平均報名 | 3–4 個管道 |
| 總報名紀錄 | ~1,750–2,000 筆（500人 × 3.5） |
| 每個管道工作表的列數 | ≈ 全學年學生數（如 600 列） |

#### 四、現行架構

##### 導師端（班級為單位）

```

        └─ 回傳至前端
```

**不採用**的方案：對每個學生逐個查詢 → 35 ×（N 個管道）× 次查詢 → 太慢。

#### 六、管理人員觀看全校 500 人之效能評估

若將同一機制擴展至管理人員檢視全校 500 人：

##### 後端時間

**與班級模式幾乎相同（~2.4–3.8s）**，原因：
- 7 個管道工作表原本就包含全校 500 人的報名資料

### 考試管道群組功能建議書

#### 現況

- `考試管道` 試算表已有 `群組` 欄位，純文字、手動填寫
- `staff_exam_pipe.html` 的 `renderPipes()` 已支援按群組分組顯示
- 缺少 UI 編輯群組的能力

#### 建議實作方向

##### 方案 A：卡牌內加輸入欄（輕量、推薦）

在每個管道卡牌的第一列新增「群組」文字輸入框，與管道全稱並排。

```
┌──────────────────────────────────────────────┐
│  管道全稱 [______________] │ 群組 [________] │
│  管道簡稱 [______________]                   │
│  ...                                         │
└──────────────────────────────────────────────┘
```

**異動範圍：**
- `renderPipes()`：群組欄位渲染
- `collectPipe()`：多收集 `群組` 值
- 前後端其餘邏輯不變

**優點：** 實作簡單（約 10 行程式碼），彈性最高，可任意命名群組。

**缺點：** 同一群組名稱需人工確保拼字一致。

##### 方案 B：下拉選單 + 管理頁面

- 在「系統設定」頁面新增群組管理（增刪改名）
- 管道編輯時改用 `<select>` 下拉選擇群組
- 群組資料可另存於 `設定` 試算表或獨立 sheet

**優點：** 名稱一致，適合多人協作。

**缺點：** 實作較重，需新增資料結構與管理 UI。

##### 方案 C：拖曳分組

- 以拖曳方式將管道卡牌拖入不同群組區域
- 群組區塊可自由命名

**優點：** 直覺。

**缺點：** 實作複雜度高，需引入拖曳庫。

#### 建議

先以 **方案 A** 快速補上 UI 缺口，未來若群組數量成長或多人協作需求浮現，再升級為方案 B。
